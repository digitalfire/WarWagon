# WarWagon project intent

## Identity and ownership
- **WarWagon** is the chosen name.
- Public GitHub repository: **digitalfire/WarWagon**.
- Independently open source. **It is not an Akrithen LLC product**.
- Do not rebrand, propose replacement names, move it under a corporate organization, or treat it as an Akrithen undertaking.

## Product ambition
Build a highly capable, extensible, autonomous security-research and assessment platform. The defining advantage should be **agent intelligence**, not dashboards, compliance workflows, prewritten checklists or mere parallel tool invocation.

Aim for: persistent and shared knowledge, graph-aware exploration, multiple competing planner strategies, dynamic specialist-agent composition, goal-directed tool use, long-running coordination, independent finding verification, reproducible experiments, model-aware routing, and meaningful improvement based on empirical results.

## User's engineering direction
- **Capability-first.** Do not allow administrative policies or restrictive-boundary discussions to dominate core research design or the roadmap. Sensible authorization, isolation and evidence integrity remain implementation requirements for testing, but are discrete infrastructure concerns.
- Do not assume one framework is best. Compare AntiFox/ARTEX, Cairn, Strix, PentAGI, PentestGPT and other systems; selectively adapt ideas and capabilities without locking the entire architecture to any one of them.
- Prefer modular contracts and a canonical framework-agnostic data model, then benchmark genuinely different cognitive approaches. Avoid premature choices of orchestrator/database/GUI.
- Avoid endless architecture-only work. **Start real code and real LLM experiments now**; decisions not blocking the vertical slice are deferred.
- Agents must critique and challenge designs, not merely approve them. Record dissent and evidence, and make consensus claims only when independently executed reviews support them.
- The user values agent-executable, extremely detailed tasks potentially numbering in the thousands, but autogenerated counts alone are not evidence of implementation readiness.

## Key product question
Which architecture produces more *verified security discoveries* with less duplicated reasoning, at comparable aggregate model/tool budgets, than a strong single-agent baseline?

## Boundaries of documented evidence
Architecture and research hypotheses are not validated product capabilities. Synthetic scheduling experiments do not measure intelligence. No production assessment platform exists yet. All testing of real services must be limited to authorized environments.
