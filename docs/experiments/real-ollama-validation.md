# WW-LIVE-007 — Real Ollama two-worker validation gate

**Implementation status:** automated local acceptance gate and report generator are implemented. A passing **actual Ollama** execution is not claimed until this command is run against the user's installed model and a report is retained.

The prior runbook and acceptance issue are [#66](https://github.com/digitalfire/WarWagon/issues/66).

## Reproducible run

From the repository root in the environment that actually hosts Ollama, identify a tool-calling model:

```bash
ollama list
```

Start the read-only event API in one terminal:

```bash
python -m warwagon.console_api --port 8765
```

Start React in another terminal:

```bash
cd console
npm install
npm run dev
```

In a third terminal, from the **repository root**, run the new acceptance harness with the exact locally installed model tag:

```bash
python -m warwagon.validation run \
  --model YOUR_INSTALLED_MODEL \
  --database artifacts/warwagon-engagements.sqlite3 \
  --workers 2 \
  --model-calls 20 \
  --tokens 100000 \
  --seconds 120 \
  --steps 8 \
  --http-rps 30 \
  --output artifacts/validation/ollama-two-worker-01.json
```

The command executes a real tool-call preflight, then the bounded localhost training-lab experiment, and audits the resulting SQLite event evidence. **No external assessment target is contacted.**

The command exits `0` only if the required event/worker/budget/observation checks pass; exits `1` if a completed run does not meet the criteria; exits `2` for preflight, input or filesystem failures. A failed run still has its own persisted engagement events, but the report might not exist if execution failed before returning from the runtime. For those cases use:

```bash
python -m warwagon.validation audit \
  --model YOUR_INSTALLED_MODEL \
  --database artifacts/warwagon-engagements.sqlite3 \
  --engagement-id THE_ACTUAL_ENGAGEMENT_ID \
  --output artifacts/validation/ollama-two-worker-failure.json
```

Inspect **Live Engagement Events** in React while the command runs. Disconnect/reconnect the browser to test SSE restoration. The audit independently reads the ledger after execution; it does not infer frontend success from a screenshot.

## What the report checks

- Terminal execution state is completed and both persisted tasks were completed.
- Exactly two distinct task IDs, two claimed worker IDs, overlapping task claims and overlapping model-call reservation-to-accounting windows are present.
- Model identity matches the chosen name in recorded `model.response` events, not a known scripted/mock model tag.
- Real recorded model-turn and allowlisted HTTP tool invocation/observation event payloads are present; observation tool-call identity matches invocation identity.
- Reserved model calls do not exceed the shared budget; every reservation has a corresponding usage accounting event and provider-reported usage is complete.
- Event IDs are ordered without duplicate sequence, target is loopback-only, and no `finding.verified` event is fabricated.
- Provider-reported token overrun is counted and warned, not hidden.

The report includes only counts, event identities and SHA-256 values; **it omits request/response bodies, raw agent output, and secrets**. Raw SQLite database and potentially sensitive model traces should remain local.

## Important limits

An agent/model name inside persisted events is **self-reported provenance, not cryptographic proof** of inference at a particular provider. The preflight sends an actual tool-call prompt to the configured endpoint, but the external endpoint could still return synthetic responses. The gate demonstrates integration consistency, not independent model reasoning quality. A fixture oracle confirms the known behavior of WarWagon's deliberately vulnerable local lab; it is not an independently verified finding on a third-party target.

Tasks remain two predefined specialist goals, not generated by an autonomous planner. Overlapping task claims and model-call reservation-to-usage windows show concurrent in-flight client operations, but do not prove simultaneous GPU inference inside the provider; provider-side request timing/telemetry is required for that. Token ceilings are soft for in-flight model calls. The run's independent security research score must be evaluated separately.

```bash
python -m unittest tests.test_validation -v
python -m unittest discover -s tests -v
```

CI uses scripted-model **test doubles only**; those are deliberately rejected by the real-model identity gate and must never be presented as completed Ollama experiments.
